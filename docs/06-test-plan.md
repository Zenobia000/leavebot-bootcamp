## 範圍、風險與策略

最重要的是「系統說成功，但紀錄或天數其實錯了」。因此用 API 驗收核對回應與資料筆數，以規則單元算例覆蓋日期邊界（TC-01 至 TC-06、TC-08、TC-10）。

- 員工資料混入或重開後遺失（高）：紀錄會失去可信度；用暫存 DB 走跨員工與重開情境（TC-07）。
- 使用者文字被當 HTML 執行（高）：以瀏覽器人工觀察並檢查 `textContent`（TC-09）。

本課以 API 驗收及少量規則單元測試為主，人工檢查畫面；沒有正式部署、負載或安全滲透測試。這些缺口需在產品化前另行補齊。

PRD 中「送出期間停用按鈕、再次獨立送出會新增一筆」尚無獨立 TC；本次不把它列為已驗證行為。若納入交付承諾，先補 AC 和案例。

## 環境、資料與判定方式

Windows 使用 `.venv\Scripts\python.exe -m pytest`；macOS/Linux 使用 `.venv/bin/python -m pytest`。套件組合依 `course/01-上課/04-STACK.md`，執行時記錄實際版本與結果。需要資料庫的自動化案例使用獨立暫存 SQLite，必要時注入 `LEAVEBOT_TODAY`。員工 1／2 為種子資料；工作日預期由日曆人工核算（2026-10-20 為週二，週五至週一為兩個工作日）。失敗案例核對 HTTP 回應和資料筆數不變，不用被測函式計算預期值。

### 成功與資料持久性

- TC-01（AC-01.1、FR-01；API）：員工 1 送出 2026-10-20 的 `annual` 整天假。預期 201、`pending`、1 天，並可在員工 1 列表看到。
- TC-07（AC-02.1、FR-06、NFR-02；API）：員工 1 送出後查員工 2，再重開 app 查員工 1。使用暫存 DB；預期員工 2 清單為空、員工 1 紀錄仍在，開發 DB 不受影響。

### 拒絕與邊界

- TC-02（AC-01.2、FR-02；API）：缺少假別。預期 422，假單筆數不變。
- TC-03（AC-01.2、FR-02；API）：結束日早於開始日。預期 422，不存檔。
- TC-04（AC-01.3、FR-03；單元）：週五到週一整天為 2 天；單日工作日上午／下午各為 0.5。跨日半天與全週末申請應拒絕。
- TC-05（AC-01.4、FR-04；API）：理由為 201 個 Unicode 字元。上限已是 100，所以 201 字回 422 且不存檔。100 與 101 的邊界見 TC-10。
- TC-06（AC-01.5、FR-05；API）：請求自行帶入 `approved` 或 `days=99`。預期 422，不存檔。
- TC-08（AC-01.2、FR-02；API）：未知員工、非法假別／時段或無效日期。各情境預期 422，不存檔。
- TC-10（AC-01.4、FR-04；API）：理由為 100／101 個 Unicode 字元。前者可登記，後者回 422 且不存檔。

### 畫面安全

- TC-09（NFR-01；人工）：理由含 HTML 標記。畫面須顯示純文字，不解析成 HTML。

## 人工驗收與缺陷處理

從首頁選員工 1，送出合法假單，核對待審核與天數；重新整理後仍可見。送出反向日期，確認錯誤且列表未新增。切到員工 2，確認看不到員工 1 的假單。以含 HTML 標記的理由送出，確認以純文字顯示。執行時記錄瀏覽器及實際結果；無瀏覽器工具時由人操作。

失敗時記測試環境、輸入、預期／實際、影響及重現步驟；修復後重跑該 TC 與相關回歸。未執行、預期紅燈和通過是不同狀態。
